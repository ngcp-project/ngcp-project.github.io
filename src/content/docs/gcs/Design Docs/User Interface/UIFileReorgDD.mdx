## Summary

- The Vue frontend leaves the top level of gcs-desktop-app and becomes the `gcs-user-interface` repo, added back as a submodule at the root. The Database (`gcs-backend`) and Software Integration (`gcs-software-integration`) DDs do the same thing for their code.
- `src-tauri/` stays at the root of gcs-desktop-app as the shared Tauri app shell. It links the Database and SI Rust code and loads the UI's built frontend. The UI repo contains no Rust.
- `src/lib/bindings.ts` is committed in the UI repo. It is the contract between the backend and the UI, so the UI repo can lint, type-check and build without the rest of the GCS.
- This move lands **before** the Database and SI file moves, so the taurpc procedures they move already point at the new bindings path.

## Background

This design doc (DD) is part of the [GCS File Reorg](/gcs/design-docs/gcs-wide/gcsfilereorgdd), which turns gcs-desktop-app into a repo of subteam submodules and reserves its top level for GCS-wide files. This doc fills in that DD's `gcs-user-interface/` placeholder.

gcs-desktop-app started as the UI project, so today the UI *is* the top level of the repo. The Vue app and all of its configs sit next to code that belongs to the other subteams and to the GCS as a whole. At [`deb007b`](https://github.com/ngcp-project/gcs-desktop-app/tree/deb007bc80a09e3cb0d353edf633b2fb8b6005bb):

| UI files | Not UI files |
| --- | --- |
| `src/`, `e2e-tests/`, `index.html`, `package.json`, `bun.lock`, `package-lock.json`, `components.json`, `tailwind.config.js`, `vite.config.ts`, `tsconfig.json`, `tsconfig.node.json`, `.eslintrc.cjs`, `.prettierrc`, `.mocharc.json`, `public/` | `src-tauri/` (Tauri shell, Database and SI Rust code), `docker-compose.yml`, `flake.nix`, `flake.lock`, `scripts/target-triple.js`, `.github/`, `.env`, `README.md`, `LICENSE`, `.gitignore`, `start.sh`, `.vscode/` |

Because of this, it is hard to tell which files belong to which subteam, and the Database and SI DDs can't settle their own paths until the UI moves out of the way.

### RFP Requirement(s)

None directly. This is an organizational change.

## Solution

The UI becomes its own repo, `gcs-user-interface`, holding only the Vue frontend and its tests. gcs-desktop-app adds it as a submodule at its root, next to `gcs-backend/`, `gcs-software-integration/` and `gcs-infrastructure/`.

`src-tauri/` stays at the root of gcs-desktop-app. It is the one place where the subteams' code comes together: it depends on `gcs-backend` and SI's Rust code by path, and `tauri.conf.json` points at `../gcs-user-interface` for the frontend.

The UI and the backend meet at exactly one file, `src/lib/bindings.ts`. taurpc generates it from the backend's procedures, and the UI imports its typed calls from it. Committing it in the UI repo makes that boundary visible: when a procedure changes, the change shows up as a diff in a UI PR.

The GCS File Reorg DD's tree names the Database folder `gcs-databse/`. This doc uses `gcs-backend/`, the repo name from the DB DD.

#### [PREFERRED] src-tauri stays at the root

`src-tauri/` is a GCS-wide app shell that wires the submodules together.

**Pros:**
- The UI repo is frontend only, so it builds on its own.
- The Rust path dependencies are siblings (`../gcs-backend`), as the DB DD already writes them.
- Database and SI developers don't need to open the UI repo to work on the shell.

**Cons:**
- Not the default Tauri layout, so `tauri.conf.json` has to point across folders, and new members need the README to find it.

#### [ALTERNATIVE 1] src-tauri inside gcs-user-interface

The default Tauri layout, `gcs-user-interface/src-tauri/`.

**Pros:**
- `tauri.conf.json` and the bindings path stay the same as today.

**Cons:**
- The UI repo would hold the Database and SI integration code, which is what this reorg is trying to undo.
- The UI repo would depend on `gcs-backend` and `gcs-software-integration`, and couldn't be built, linted or reviewed without them.

### What moves, what is deleted

| --- | --- | --- |

| `package-lock.json` | Deleted | Bun is the package manager (README, CI, `tauri.conf.json`). The npm lockfile is stale and nothing reads it. |

### Paths that cross the boundary

These are the only places where the UI and the rest of the GCS refer to each other's paths. They change in the same PR as the move.

| File | Change |
| --- | --- |
| `src-tauri/tauri.conf.json` | `frontendDist` is now `../gcs-user-interface/dist` (see below). |
| Every `#[taurpc::procedures(export_to = …)]` | `"../src/lib/bindings.ts"` becomes `"../gcs-user-interface/src/lib/bindings.ts"`. Today these are in `commands/commands.rs` and `telemetry/rabbitmq/mod.rs`. The path is relative to `src-tauri/` at runtime, so it stays correct when SI and Database move those files into their own repos. |
| `gcs-user-interface/package.json` | `"tauri": "cd .. && tauri"`, so the Tauri CLI runs from the root where `src-tauri/` is. The `osm:*` scripts are removed, because starting Docker services is the centralized start's job. |
| `gcs-user-interface/e2e-tests/helpers/driver.ts` | One more `'..'` to reach `src-tauri/target/debug/Interface`. `setup.ts` doesn't change, because the `tauri` script already runs from the root. |
| `.github/workflows/e2e-tests.yml` | Check out with `submodules: recursive`, and run the Bun steps with `working-directory: gcs-user-interface`. |

```diff
// src-tauri/tauri.conf.json
  "build": {
    "beforeBuildCommand": "bun run build",
    "beforeDevCommand": "bun run dev",
    "devUrl": "http://localhost:4000",
-   "frontendDist": "../dist"
+   "frontendDist": "../gcs-user-interface/dist"
  },
```

The `before*Command` hooks don't change. When the Tauri CLI (2.0.0) runs from the root, it finds `src-tauri/tauri.conf.json` and `gcs-user-interface/package.json` on its own and runs the hooks in the UI folder. `tauri.conf.test.json` doesn't change either.

### taurpc bindings

The Vue stores import every backend call from `src/lib/bindings.ts`. Today taurpc writes it whenever the app starts in debug mode, and it is gitignored. That works only because the UI and `src-tauri/` are in the same repo. On its own, a fresh clone of the UI repo can't type-check, since `bun run build` runs `vue-tsc`.

After this move, `bindings.ts` is committed in the UI repo:

- Whoever changes a taurpc procedure runs the app once (`bun run tauri dev`), which rewrites `gcs-user-interface/src/lib/bindings.ts`, and commits the new file in the UI repo along with the submodule bump in gcs-desktop-app.
- The UI repo's CI runs `bun install`, `bun run lint` and `bun run build` with no Rust, Docker or backend.
- The e2e workflow in gcs-desktop-app builds the app, which regenerates the bindings, and fails if `bindings.ts` changed (`git diff --exit-code`). That catches a procedure change that wasn't committed to the UI.

This doesn't decide who owns the taurpc procedures. That question is open in the DB DD. The UI only depends on the generated file.

### Migration order

1. **Move inside gcs-desktop-app (one PR).** `git mv` the UI files into `gcs-user-interface/`, make the deletions and path changes above, commit `bindings.ts`, and add the UI's `.gitignore`, `README.md`, `.env.example` and CI. The app runs the same as before, now from a folder. This only touches two lines inside `src-tauri/src`, so it doesn't conflict with the Database team's work there.
2. **Turn the folder into the submodule.** Unarchive [ngcp-project/gcs-user-interface](https://github.com/ngcp-project/gcs-user-interface) and tag its current `main` (for example `archive/2025`) so the old history stays reachable. Then push `git subtree split --prefix=gcs-user-interface` as its new `main`, and replace the folder in gcs-desktop-app with `git submodule add https://github.com/ngcp-project/gcs-user-interface gcs-user-interface`. No paths change in this step.
3. **Database and SI moves.** The procedures they move already have the new `export_to` path.
4. **Centralized start (GCS File Reorg DD).** It starts the Docker services and runs the app from the root. The UI no longer starts any services.

### Out of scope

These came up while planning the move and belong in their own DDs or PRs:

- Reorganizing `src/` (component folders, stores in `lib/`, naming).
- Cleanup in `vite.config.ts` (Tauri v1 env variable names) and `package.json` (test packages in `dependencies`).
- Offline map tiles. `public/Atlases/SLO/` is deleted with `public/`, and isn't read by any code today.
- Replacing the OpenCV sidecar (DB DD).

## Open questions

- Who owns `src-tauri/` (`main.rs`, `tauri.conf.json`, capabilities, icons) as the GCS-wide shell? This is closely tied to the DB DD's question of who owns the taurpc procedures.
- The GCS File Reorg DD uses `gcs-databse/`, and the DB DD uses `gcs-backend/`. The GCS-wide tree should be updated to match.

## Unit/End to End Testing

This is a refactor, so no new test cases are added. The move is done when:

- On a fresh clone of `gcs-user-interface` alone: `bun install --frozen-lockfile`, `bun run lint` and `bun run build` pass. The build runs `vue-tsc`, which confirms that the committed `bindings.ts` is enough.
- On a fresh `git clone --recursive` of gcs-desktop-app, with the services running: `bun run tauri dev` from `gcs-user-interface/` opens both windows (Camera Screen and Over View), and the map, mission and telemetry views load data.
- Running the app rewrites `gcs-user-interface/src/lib/bindings.ts` with no diff.
- `bun run tauri build` produces a bundle that loads the frontend from `gcs-user-interface/dist`.
- `bun run test` passes the existing e2e specs (`map-annotations.spec.ts`, `mission-menu.spec.ts`) locally and in the gcs-desktop-app workflow.
