## Why we need schema migrations

Right now `init_db.rs` builds the database with `CREATE TABLE IF NOT EXISTS` every time the app starts. That only works on a brand-new database: if a table is already there, Postgres skips the statement, so a new column or table never reaches a database someone already has. Almost everything new in this design needs schema changes. Replay (GCS_23 to GCS_25) needs a receive time and mission id on every telemetry row, survivor and fire reports have to be saved so they survive a restart, and zones move from hand-formatted `"(lat,long)"` strings to JSONB. With `sqlx::migrate!`, each change is a numbered SQL file in `migrations/`. On startup the app runs the ones that haven't run yet, in order, and sqlx records which ones have. `0001_baseline` is today's four tables, so it applies cleanly to the databases we already have, and every later change reaches every machine the same way. The dummy data that `init_db.rs` inserts moves to `dev/seed.rs` and is off by default. A merged migration is never edited; a fix goes in a new one.

## The restructure

Today the database code lives in `src-tauri/src`, mixed in with the RabbitMQ and UI code, and mission and vehicle state is kept in five places, each with its own lock: `MissionApiImpl`, the `LAST_STATE` and `KEEP_OUT_ZONES` globals, `RabbitMQAPIImpl` and `CommandsApiImpl`. Those copies drift apart. For example, `start_mission` never updates `LAST_STATE`, so the geofence and survivor checks keep using whichever mission was active at launch. The idea is to move all of it into one `gcs-backend` crate that the Database team owns, with a State Manager in `state/` as the single owner of that state. Every change goes through it in the same order: check that the change is allowed, save it to Postgres, update memory, publish an event to the UI, then send any vehicle command. The folders are split by job, so `state/` is the only code that changes live data, `db/` is the only code that runs SQL, and `domain/` holds the types and rules and can be tested on its own. The UI keeps calling the same taurpc procedures. The RabbitMQ code goes to SI, and it talks to the State Manager through `apply_telemetry` and a `CommandSender` interface. The code changes happen inside today's `src-tauri` first, one PR at a time with the app still running, and the files move into `gcs-backend` last.

## Issues that could arise

- SI has to agree to the interface (`apply_telemetry`, `CommandSender` and a consumer for `command_ack`). The SI DD also moves the message types in `telemetry/types.rs` to SI, so we need to decide which crate owns them. If SI hasn't agreed by `<date>`, the Database team writes that code inside `src-tauri` and hands it to SI when the files move.
- `0002` has to change the `-1` stage ids to `NULL` before it adds the foreign key, or it fails on any database with a vehicle that has no stage, which includes every new mission. From `0002` on, migrations are forward-only, so undoing one means resetting your dev database.
- The new Postgres service uses a pinned image and a named volume (`ngcp_pgdata`), so everyone starts on a fresh database. Dev data from before that change isn't carried over.
- With one writer, operator changes wait on each other and on the database. In our benchmark a telemetry insert took about 2.4 ms, so three vehicles at 1 Hz shouldn't be a problem. If Postgres goes down, changes that need saving return an error, while telemetry and the emergency stop keep working from memory.
- The layout isn't settled: where `src-tauri` goes, who creates the `gcs-backend` repo, and who owns the taurpc procedures (the SI DD moves some of the files that define them). The file move waits on those answers, and after it taurpc still has to write `src/lib/bindings.ts` into the UI folder.
