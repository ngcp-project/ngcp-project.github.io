## Background
This DD is a part of the effort to reorganize the gcs-desktop-app repo. See [GCS File Reorg Design Doc](/gcs/design-docs/gcs-wide/gcsfilereorgdd) for more information. The branches on gcs-desktop-app and the SI repo also needs some clean up (deprecated files, etc.)

## Solution
The software integration repo will be reorganized and restructured to account for files moving from the gcs-desktop-repo. The aim is to increase clarity and organization.

Changes will be made accordingly to ensure it does not break the existing application.

Unit tests should be set up to ensure everything is functioning. 

## Design/Implementation

The repo will be renamed from `GCS-Integration-Library-2025-26` to `gcs-software-integration` to follow the naming conventions of the other submodule repos. 

All other subsequent files, folders, and class names will be converted to snake_case. 

There will be 2 parts to consider for the restructuring.

The existing code in [GCS-Integration-Library-2025-26](https://github.com/ngcp-project/GCS-Integration-Library-2025-26/tree/077bf1dbb88307fc44a9181a9ccbbbbcc541b19a) which contains the python program that interacts with the hardware (xbees). And [gcs-desktop-app/src-tauri/src](https://github.com/ngcp-project/gcs-desktop-app/tree/deb007bc80a09e3cb0d353edf633b2fb8b6005bb/src-tauri/src) which contains the rust code that interacts with the state manager.

### Interfacing with other teams
Once everything is moved, we need to ensure it doesn't break the whole application (Expecially the rust side).

This aims to outline how our team will interface with other teams.

## Unit/End to End Testing
List out what cases and edge cases you will be testing. If you are refactoring, no need to list the cases, just make sure it passes existing test cases. 

Unit tests would be like testing normal and edge cases for newly introduced methods or a small part of the flow. The test file should be named after the file you are testing (yourFileTest.x) and located in a testing folder (create one if it does not exist). If applicable, you may use a testing framework. 

End to end testing would be test files that test the entire process from point A to point B. This may be cross-team, endpoints/interfaces that your subteam has with other teams, etc. Include this if applicable.
